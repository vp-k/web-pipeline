# 프로젝트에 집중하기

파이프라인은 제품 변경을 기록·검증하는 수단이다. 도입 요청이 제품 개발도 포함하면 첫 산출물은 사용자가 요청한 실제 기능 하나의 동작과 검증이다. 파이프라인 개선 자체가 요청된 경우만 엔진 개발을 한다.

1. 기존 실행 진입점·패키지 스크립트·테스트·요구사항을 읽고 첫 기능의 수용 기준을 잡는다. 기존 구조를 유지한다.
2. 실제 범위의 `--domains`를 명시한다. 예시의 전체 도메인·결제·운영·배포는 할 일 목록이 아니다. 존재하는 보안/개인정보/DB 요구사항은 빠뜨리지 않는다.
3. `sources` 6개는 정보 역할이다. 기존 문서를 가리킬 수 있으며 여러 역할이 하나의 실질적인 문서를 참조해도 된다. 형식만 채우는 장문 문서를 새로 만들지 않는다. task의 6개 기획 항목도 간결한 실제 근거로 채우고 질문을 만들어내지 않는다.
4. 기존 테스트·빌드 명령을 argv로 연결한다. 첫 기능에 필요한 빠진 검증만 추가한다. 기존 필수 검증을 끄거나 가짜 성공을 넣지는 않는다. 소스 증거가 유효하면 같은 준비 검사를 반복하지 않는다.
5. 작은 기능은 여러 계층을 포함해 작업 하나로 처리할 수 있다. 독립적인 완료 단위가 있을 때만 여러 task와 Phase로 나눈다. 분할된 멤버의 검증이 서로 구현을 요구할 때 implementation group을 사용한다.
6. 준비 조건을 갖추면 바로 기능을 구현한다. 범용 어댑터·새 CI·새 플러그인·리포트 시스템은 요청되었거나 실제 기능을 막는 구체적 문제가 있을 때만 다룬다. 엔진 결함이면 재현·영향을 좁혀 보고하고 기존 안전한 경로를 먼저 사용한다.
7. 첫 기능을 실제로 검증한 뒤 남은 요청 기능으로 이어간다. 진행 보고에는 어떤 제품 동작을 완성했는지, 설정이 남았다면 어떤 기능을 막는지 적는다. 설치 성공이나 문서 수를 제품 진척으로 제시하지 않는다.

빈 프로젝트의 최소 실행 스캐폴드와 진짜 테스트 준비는 필요하다. 기존 프로젝트를 새로 도입하거나 세션을 재개할 때 그 준비를 처음부터 다시 하지 않는다. 인프라·Release는 명시적으로 요청받았을 때만 범위에 포함한다.
