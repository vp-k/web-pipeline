# 반복 중단과 제품 개발 지연 점검 — 2.12.0

점검 범위는 엔진의 승인·기획·시간/실패 예산·큐·리스·의존성·Git·보관·검증/Release 게이트, 배포용 명령/스킬/거버넌스/런북, 보관된 Codex 스킬 원본이다. 사용자 사례인 `ai-cs-new`의 기존 정책·상태·큐 이력도 읽기 전용으로 확인했다. 이 문서는 제품 작업의 STATE나 승인 기록이 아니다.

| 원인 | 수정 또는 유지 근거 |
| --- | --- |
| AWAITING_USER를 곧바로 재질문으로 해석 | 엔진 `CHECK_EXISTING_CONSENT`와 지침으로 기존 실제 동의·현재 바인딩 확인을 우선한다. 누락된 전사는 복구한다. |
| 모든 리뷰에 fresh response가 필요하다는 해석 | 보호 대상의 새 결정에 한정한다. 일반 standard 로컬 리뷰와 유효한 기존 동의에는 질문이 없다. |
| 옛 review-request/handoff를 현재 대기로 오인 | 현재 STATE·큐·새 진단을 우선한다. 과거 요청 파일은 기록으로 남긴다. |
| 기획 기록 오류를 사용자 질문으로 전환 | `REPAIR_RECORD`와 `CHECK_EXISTING_REQUIREMENTS`를 구분한다. 실제 미해결 요구사항은 계속 막는다. |
| 누적 시간 120분마다 중단·갱신 질문 | 새 도입은 warn. 사용량과 경고를 보존하며 실행한다. 기존 미지정 설정/큐는 enforce를 유지한다. |
| 순수 시간 예산 중단이 실패 횟수도 소진 | 순수 budget BLOCKED만 실패 예약분을 환불한다. 혼합 실패·명령 timeout·불명확한 결과는 기존 한도를 소진한다. |
| WAITING/FAIL이면 즉시 턴 종료 | 원인 조사와 요청 범위의 수리·기록·환경 복구를 먼저 수행한다. 게이트를 우회하지 않는다. |
| ACTION_REQUIRED를 사용자 허락으로 오인 | 에이전트 액션임을 명시하고 complete→next를 이어간다. |
| 세션 재개·단계 전환·다음 작업마다 확인 | 유효한 범위·증거·기존 요청을 재사용한다. |
| Git 실패가 승인된 충돌 해결까지 막음 | 새 기능을 보류하되 같은 요청 안의 안전한 통합 해결을 계속한다. 변경 폐기나 미정 내용은 별도 결정이다. |
| 시간 경고 수집이 NOT_READY 상태의 기존 리스 조회를 가림 | 경고 수집은 실행 준비 게이트를 재요구하지 않는다. 실제 액션의 준비 게이트는 유지한다. |
| BUSY·리스·락 문제의 자동 사용자 전가 | 프로세스/효과를 조사하고 종료가 확인된 리스만 복구한다. 살아 있는 작업을 가로채지 않는다. |
| 서브에이전트가 없으면 일반 리뷰 불가 | 별도의 실제 로컬 검토를 수행하고 자체 리뷰임을 기록한다. 사람·독립 리뷰를 대신했다고 주장하지 않는다. |
| 선택적 보관을 최종 승인과 묶음 | 분리한다. 명시적 범위의 일괄 보관 요청은 재사용하되 매번 기존 archive 게이트를 검증한다. |
| 일반 개발에 Release 준비까지 요구 | `load_config`의 개발 준비 검사를 Policy/Baseline/Fast/Full로 제한한다. Release 실행은 여전히 전용 검사·승인을 요구하고 disabled는 NOT_RUN이다. |
| 전체 도메인 기본 예시를 전체 구축 목록으로 해석 | 실제 도메인을 명시하고 기존 검사/문서를 연결하도록 도입 지침을 수정했다. 도메인을 자동 추측하거나 실제 보안 책임을 제거하지 않는다. |
| 6개 source 역할마다 새 문서를 작성 | 기존 실질적 문서를 재사용하고 여러 역할이 같은 문서를 가리킬 수 있음을 명시했다. 기획 항목 수도 질문 수가 아니다. |
| 작은 연결 기능도 task+Phase+group으로 강제 분할 | 한 작업으로 여러 계층을 구현할 수 있다. 이미 나눈 멤버들의 검증이 서로 구현에 의존할 때만 group을 사용한다. |
| 도입 요청에 별도 시범 기능 추가 | 구현까지 요청된 경우 실제 요청 기능을 첫 검증 대상으로 삼는다. 도입만 요청되면 설정으로 끝낸다. |
| 모든 설정·범용 어댑터·CI를 먼저 완성 | 구체적 제품 기능을 막는 설정만 수행한다. 기존 준비/검증 증거를 재사용하고 준비 후 곧바로 첫 기능으로 이동한다. |
| 재개 요청을 받았는데 다시 갱신 허락 질문 | 이미 받은 구체적 요청 범위에서 한정된 갱신을 실행한다. 무제한 자체 갱신은 허용하지 않는다. |

계속 유지하는 중단 조건은 실제 미해결 요구사항, 유효한 보호 결정/서명 부재, 철회, 실제 외부 자격 증명·권한 부재, 확인되지 않은 프로세스 소유권, 증거 훼손·stale binding, 실패/동일 실패/외부 재시도/스텝 강제 한도, 명시적 사용자 중지다. `revise`, `retry`, `recover`는 감사 가능한 명령이며 이미 승인된 복구까지 다시 허락받으라는 의미는 아니다.

새 정책은 현재 저장소의 엔진·배포 원본 2.12.0에 반영한다. 기존 프로젝트와 설치된 다른 플러그인 사본은 이 저장소 편집으로 자동 업데이트되지 않는다. 특히 기존 `time_budget_mode`가 없으면 enforce다. 프로젝트 적용 시 관리형 upgrade 미리보기/백업을 사용하고 프로젝트 소유 거버넌스·설정은 차이를 통합한다. 준비된 fingerprint/완료 증거가 무효화될 수 있으므로 활성 작업·리스·기존 기록을 보존하고 정상 재검증 경로를 따른다. 설치 영수증이나 현재 STATE를 손으로 고쳐 통과시키지 않는다.

검증은 실제 fixture 기반 전체 엔진/배포 테스트, 정적 검사와 배포 매니페스트 검사로 수행한다. 사용자 승인 횟수나 제품 개발 시간의 실측 개선율은 아직 측정하지 않았다.

구체적 재현: Release 전용 fixture를 disabled로 두면 이전 엔진은 `prepare` 단계부터 `Required project command ... is disabled`로 거부했다. 새 회귀 테스트는 개발 DONE까지 통과한 뒤, 같은 설정의 Release에서 그 검사가 NOT_RUN이고 release_status가 NOT_READY인지 확인한다. 기획 진단도 기록 오류와 실제 미해결 질문을 분리하는 테스트를 추가했다.

최종 검증 결과:

- 전체 테스트 `python tools/test.py -j 6`: 27개 모듈 실행. 26개 통과, 새 Release 테스트 fixture의 사전 설정이 작업 변경으로 분류되어 1개 실패했다. 사전 설정을 fixture 기준 커밋에 포함한 뒤 해당 회귀 테스트가 통과했다.
- 상태 조회 보완 후 `python tools/test.py time_budget release_integration distribution -j 3`: 3/3 모듈, 22개 테스트 통과. 전체 테스트 목록은 280개이며 최종 변경의 관련 재검증까지 완료했다.
- `ruff check ... --select F,E9`: 통과. `mypy ... --ignore-missing-imports`: 27개 소스 파일 오류 없음.
- `scripts/pipeline.py doctor`, `tools/release.py --check`, `git diff --check`: 통과. 배포 버전 2.12.0, kit 파일 108개.

이번 수정은 현재 파이프라인 저장소 원본에 적용했다. 사례로 조회한 `ai-cs-new`의 코드·설정·엔진·작업 상태·승인·검증 증거에는 쓰기 작업을 하지 않았다.
